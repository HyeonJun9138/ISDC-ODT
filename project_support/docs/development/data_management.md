# 데이터 관리 탭과 데이터 관리 모듈 (ICD-01)

데이터 관리 모듈은 우주 데이터 센터의 **데이터 수명주기 관리자**다. 위성과 지상에 흩어진 저장 노드 위에서 어떤 데이터 객체가 어디에 몇 벌 있고, 그 사본이 온전한지, 서비스 요청이 오면 어느 사본에서 얼마의 지연으로 제공되는지를 결정하고 보고한다. 디지털 트윈은 이 모듈의 상태를 데이터 탭에 표시한다. 현재 콘솔은 사용자가 실제로 배치하고 서버가 수락한 SDC 위성의 저장소와 SIM 데이터만 등록한다. 고정 SAT-01~05와 지상 데이터센터, 게이트웨이 예제는 콘솔 입력에서 제외한다.

## 데이터 패브릭(ICD-02)과의 구분

두 모듈은 이름이 비슷하지만 책임이 겹치지 않는다.

| 구분 | 데이터 관리 (ICD-01) | 데이터 패브릭 (ICD-02) |
|---|---|---|
| 다루는 것 | 데이터 객체의 정체성과 사본 | 비트의 이동 경로 |
| 질문 | 이 데이터가 어디에 몇 벌 있고 온전한가, 요청하면 어디서 주는가 | 지금 이 노드에서 저 노드로 어떤 링크를 거쳐 얼마의 지연으로 보낼 수 있는가 |
| 상태 | 카탈로그, 복제본 배치, 체크섬, 보존 기간, 서비스 이력 | 링크 품질, 경로표, DTN 백로그 |
| 시간 기준 | 트윈 시뮬레이션 경과 초 | 트윈 분석 시각(UTC) |
| 입력 | 저장 노드 명세와 가용성, 생성된 데이터 제품 | 노드와 링크의 기하, 단말 상태 |

패브릭은 "이 바이트를 어떻게 보낼까"를, 데이터 관리는 "이 데이터를 어디에 두고 언제까지 지키며 누구에게 줄까"를 답한다. 데이터 관리는 사본을 옮길 때 패브릭의 경로를 쓴다고 가정하지만, 현재 구현에서 두 모듈은 서로를 호출하지 않는다.

## 화면 사용

왼쪽 위는 모듈 연결 상태다. 내장 임시 구현인지 외부 모듈인지, 구현과 버전, 모듈이 진행한 시뮬레이션 시각, 마지막 동기화에서 보낸 노드 수와 제품 수를 보여준다. 그 아래는 저장 노드 목록으로 배치된 SDC의 사용률과 보관 객체 수를 표시한다. 저장 장치가 없거나 비활성인 노드는 용량 0과 저장소 미설정으로 표시하며 데이터를 생성하지 않는다. 노드를 누르면 카탈로그가 그 노드에 사본을 둔 객체만 남기고, 다시 누르면 해제된다.

가운데 위는 **데이터 안정성 점수**(0~100)와 구성 요소다. 노드 가용 30 %, 복제 충족 25 %, 정합성 20 %, 서비스 성공 15 %, 용량 여유 10 %의 가중 평균이며 90 이상은 안정, 70 이상은 주의, 그 아래는 불안정으로 표시한다. 오른쪽 타일은 수집 처리율, 데이터 객체 수, 검증 복제본 비율, 저장 사용률, 진행 중인 자가복구, 복제 부족·위험 객체 수다. 그 아래 줄은 활성 경고다. 배치나 데이터가 없으면 점수는 100이 아니라 평가 대기다. 용량과 복제본의 분모가 0이면 해당 비율은 미평가로 반환한다.

가운데 가운데는 파이프라인이다. 최근 5분 동안 수집 → 추출·필터 → 저장·분산 → 복제·동기화 → 서비스 각 단계를 통과한 건수를 막대로 보여주고, 그 아래 세 그래프는 수집 처리율, 평균 복제 지연, 평균 서비스 지연의 추이다.

가운데 아래는 데이터 카탈로그다. 종류 필터와 검색으로 좁히고, 행마다 객체 ID, 종류, 생성 노드, 크기, 복제(검증/목표), 정합성, 저장 계층(핫·웜·콜드), 상태, 등록 시각을 보여준다. 행을 누르면 오른쪽에 상세가 뜬다.

오른쪽 위는 선택 객체의 상세다. 체크섬, 보존 기간, 마지막 검증 시각, 서비스 횟수와 복제본이 어느 노드에 어떤 상태(검증됨, 동기화 중, 재검사 대기, 접근 불가, 손상, 유실)로 있는지 보여준다. `무결성 검사`와 `재복제`로 이 객체만 조치할 수 있고, `서비스 요청`은 지정한 노드가 이 객체를 요청했을 때 어느 복제본에서 얼마의 지연으로 제공되는지 확인한다. 실제 전송은 하지 않는다.

오른쪽 가운데는 운영 조치다. 무결성 검사, 자가복구, 재균형, 만료 정리와 데이터 종류별 복제 계수 변경이 있고, `DT 스냅샷 제외`는 비활성이다. DT 자체 스냅샷은 SDC 데이터와 출처 및 보관 정책이 달라 자동 생성과 수동 등록에서 제외했다. 그 아래는 진행 중인 작업의 진척이다. 오른쪽 아래는 이벤트 목록이며 등급으로 걸러 볼 수 있고, 객체가 연결된 이벤트를 누르면 그 객체가 선택된다.

## 모델

### 데이터 객체와 복제본

객체는 등록된 데이터 제품 하나다. 종류마다 복제 계수, 보존 기간, 핫 계층 유지 시간, 우선순위가 정해져 있다(관측 영상·과학 관측 3벌, 텔레메트리·임무 로그·운용 스냅샷 2벌). 복제본은 저장 노드 하나에 놓이며 상태는 `검증됨`, `동기화 중`, `재검사 대기`, `접근 불가`, `손상`, `유실`이다. 검증된 복제본만 복제 계수 충족으로 센다.

객체 상태는 복제본에서 유도한다. 검증된 사본이 없고 진행 중인 복사도 없으면 `위험`, 손상이 있으면 `복제 부족(정합성)`, 목표에 못 미치지만 복사가 진행 중이면 `대기`, 목표를 채웠으면 `정상`이다. 복사 중인 상태를 장애로 표시하지 않는다.

### 배치와 서비스

원본 사본은 생성 노드에 두고(용량이 있으면), 나머지는 지상 코어 → 엣지 → 탑재 순으로 여유 용량이 많은 노드에 하나씩 놓는다. 한 노드에 같은 객체의 사본을 두 벌 두지 않는다. 서비스 요청은 검증된 사본 중 지상 코어 → 엣지 → 탑재 순으로 가장 빠른 노드에서 제공하며, 지연은 노드 종류별 기본 지연(코어 40 ms, 엣지 80 ms, 탑재 450 ms)에 크기 ÷ 노드 종류별 전송률(2000 / 800 / 200 Mbps)을 더한 값이다. 대표 공학값이며 실제 저장 시스템 성능이 아니다.

### 정합성과 자가복구

주기 무결성 검사(기본 300초)는 검증된 사본의 체크섬을 다시 확인하고, 일정 확률로 불일치를 발견한다. 불일치가 나오면 그 사본을 `손상`으로 바꾸고 다른 노드에 새 사본을 만드는 복구 작업을 시작한다. 노드가 사용 불가가 되면 그 노드의 사본은 `접근 불가`가 되고, 유예 시간(기본 60초)이 지나도 복귀하지 않으면 다른 노드에 복구한다. 노드가 돌아오면 그 사본은 `재검사 대기`로 두었다가 재동기화한다. 복구 속도와 동기화 속도는 정책값(기본 400 / 800 Mbps)이다.

### 트윈이 등록하는 데이터

서버가 수락한 배치 노드의 활성 `dtn_store` 한 개당 2000 GB를 사용한다. 가용 저장소가 있는 노드에서 텔레메트리는 30초 간격으로 8~24 MB, 활성 `eo_camera`가 함께 있으면 관측 영상은 90초 간격으로 400~1200 MB를 생성한다. 동일 참조와 시각 구간은 같은 크기를 산출하는 SIM 메타데이터이며 실제 영상 파일이나 실측 텔레메트리가 아니다. 과학 관측과 임무 로그는 대응 모델이 없으므로 자동 생성하지 않는다.

배치 수락 시각 이전의 데이터는 만들지 않는다. 초안 생성이나 궤도 카탈로그 조회만으로는 데이터가 생기지 않는다. 현재 배치 ID와 실행 ID로 카탈로그, 복제본, 작업, 이벤트의 범위를 분리한다. 재배치와 회수 후 현재 화면에는 새 범위만 표시하며 과거 범위나 외부 공유 데이터를 삭제하지 않는다. 장애 상태는 기존 SIM 장애 입력을 사용하며 가용하지 않은 노드에서는 생성을 중단한다.

### 배치 수락과 범위 계약

`GET /api/data-management/deployment`는 현재 서버 사본을 반환한다. `POST` 입력은 `deployment_id`, `expected_revision`, `nodes`이며 노드마다 `id`, `name`, `mode`, `equipment`를 보낸다. 장비는 `id`, `catalog`, `enabled`를 사용하고 최대 240개 노드를 허용한다. 응답은 수락된 구성과 `revision`, `run_id`, `scope_id`다. 버전이 다른 요청은 409, 동일 ID와 내용의 재전송은 멱등 처리한다. 모듈이 수락하지 못하면 runtime 배치를 바꾸지 않는다.

브라우저는 서버 수락 후에만 로컬 배치를 확정한다. 첫 서버 revision 0에서만 저장된 로컬 배치를 복원하며 다른 브라우저가 수락한 배치를 자동으로 덮어쓰지 않는다. 실패 시 초안과 기존 배치를 유지하고 재시도를 안내한다. 데이터 탭은 범위가 바뀌면 선택 객체, 필터 대상 노드, 이벤트 커서와 추세를 비우며 새 범위를 `after=0`부터 읽는다. 늦은 이전 응답은 무시한다.

ICD 요청과 응답은 `scope_id` 및 `scope_contract: isolated-v1`을 사용한다. 콘솔 조치와 서비스 요청은 현재 `scope_id`를 보내야 하며 다른 범위이면 409다. 외부 모듈은 같은 범위 계약을 지원해야 한다. 미지원이나 범위가 다른 응답은 연동 실패로 처리하며 내장 예제나 정상 결과로 대체하지 않는다. 기존 범위 없는 ICD 클라이언트는 이 계약에 맞춰 갱신해야 한다. 기존 알고리즘 시험용 고정 예제 함수는 명시적 fixture에서만 유지한다.

## 실행 방식

기본은 내장 실행이다. `create_app()`이 범위별 `DataManagementStandIn`을 제공하는 `ScopedDataManagement`를 만들어 `/api/data-management/*`에 연결한다. 별도 프로세스의 데이터 관리 모듈을 쓰려면 같은 ICD를 제공하는 주소를 지정한다.

```powershell
python main.py --data-management-url http://127.0.0.1:8793
```

이 경우 `communication/external/data_management.py`가 요청을 그 주소로 전달하고, 응답이 없으면 대시보드에 외부 모듈 응답 없음으로 표시하며 조치 요청은 503으로 보고한다. 이 저장소에서는 두 번째 SpaceTwin 인스턴스가 같은 ICD를 제공하므로 외부 연결 경로를 실제로 시험할 수 있다.

## 한계

값은 대표 공학값이며 실제 저장 시스템의 성능, 실제 복제 지연, 실제 정합성 오류율이 아니다. 무결성 손상은 정책값 확률로 발생시키는 모의이고 실제 비트 오류 관측이 아니다. 배치는 용량과 종류만 고려하며 랙·전원·지리적 장애 도메인을 구분하지 않는다. 서비스 요청은 어느 사본에서 얼마의 지연으로 줄 수 있는지를 계산할 뿐 실제 데이터를 전송하지 않으며, 사본 이동에 필요한 네트워크 경로는 데이터 패브릭이 따로 계산한다. 카탈로그와 이벤트는 모듈 프로세스의 메모리에 있으며 영구 저장이나 replay가 아니다.
