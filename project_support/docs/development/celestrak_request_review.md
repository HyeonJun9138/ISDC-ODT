# CelesTrak 반복 요청 검토

2026-09-08 현재 코드에 대한 검토다. 서버는 재실행하지 않았다. CelesTrak GP 및 SATCAT 데이터 API를 실제로 호출하지 않았으며, 공식 문서만 웹 도구로 확인했다. 재현은 httpx.MockTransport와 임시 캐시를 사용했고 시험 구간의 소켓 연결은 차단했다. 운영 코드와 기존 캐시 파일은 변경하지 않았다.

## 결론과 확인 범위

현재 GP 성공 캐시는 7200초다. 따라서 모든 화면 조회가 곧 외부 다운로드인 것은 아니다. 그러나 실패 이후의 정지 상태, 재시도 대기 시간과 공통 요청 차단이 없어 캐시가 만료되었거나 없을 때 사용자의 조회가 계속 외부 요청으로 이어진다. 이 경로는 재현했다. 실제 이 PC가 2시간 안에 50개 오류를 보냈는지, CelesTrak 방화벽 차단의 유일한 원인인지는 확인할 수 없다. 남아 있는 로그는 주로 우리 서버가 받은 요청만 기록하며, 상류 응답 코드와 요청 시각을 지속적으로 기록하지 않는다.

확인한 로그 5개에는 /api/satellites 계열 로컬 요청이 합계 21건 있었다. 서로 다른 검증 실행과 시점이 섞여 있고 원래 운용 서버의 전체 로그가 아니므로 전체 외부 요청 수로 해석하면 안 된다. 기존 Active 디스크 캐시의 fetched_at은 2026-09-07T10:57:23+00:00, Stations는 2026-09-07T12:14:37+00:00였다. 여러 다른 그룹 캐시도 더 오래되었다. 따라서 이후 새 브라우저나 검증 서버에서 카탈로그를 읽을 때 유효기간이 지난 캐시를 갱신하려 했을 가능성이 있다. 앞선 검증용 서버와 브라우저 사용도 같은 공인 IP의 요청에 기여했을 가능성을 배제할 수 없다.

## 주요 발견

### P1. GP 실패 이후 요청을 멈추지 않는다

`data/catalog/access.py:41–70`은 성공했을 때만 캐시 시각을 갱신한다. 403 또는 503이면 이전 스냅샷이나 빈 결과를 반환하지만 실패 시각, 다음 허용 시각, 응답 코드 기반 정지 상태를 저장하지 않는다. 이후 호출은 같은 fetch_gp를 다시 실행한다. 그룹별 asyncio.Lock은 한 인스턴스 안의 동시 실행을 순서대로 처리할 뿐, 실패한 요청들을 하나로 합치거나 이후 요청을 차단하지 않는다.

50번 조회하는 모의 시험에서 성공 시에는 외부 시도 1회, 최초 403이나 만료 캐시의 403/503에서는 각각 50회였다. 같은 인스턴스에 동시 요청 50개를 주어도 403 응답 50회가 발생했다.

### P1. SATCAT 실패와 다른 조회 경로가 동일 IP의 요청을 추가한다

`data/catalog/access.py:78–98`에서도 실패를 캐시하거나 이후 조회를 중단하지 않는다. 같은 상세정보를 50번 요청하며 404를 반환하면 외부 시도도 50번이다. GP가 실패했다고 SATCAT 조회를 멈추는 공통 상태도 없다. `user_application/web/scripts/orbit/inspector.js:233–249`의 브라우저 캐시도 성공한 SATCAT만 보관하므로 상세정보 재선택 때 실패 요청이 다시 발생할 수 있다.

SATCAT 성공 캐시는 24시간이지만 서버 메모리에만 있다. 새 Catalog 인스턴스 두 개가 같은 위성의 성공 응답을 조회하면 같은 디스크 경로를 사용해도 외부 시도는 두 번이었다. 이는 SATCAT의 중복 요청 위험이며 GP의 2시간 주기를 SATCAT에 그대로 적용한다는 뜻은 아니다.

### P1. 여러 서버의 동시 다운로드와 실패 상태를 조정하지 않는다

`data/catalog/access.py:18–23`의 잠금과 메모리 캐시는 인스턴스별이다. GP 성공 파일은 공유하지만 여러 인스턴스가 빈 파일 또는 만료된 파일을 동시에 확인하면 둘 다 다운로드할 수 있다. 같은 디스크 폴더를 사용하는 두 인스턴스의 동시 성공 조회에서 외부 시도 두 번을 재현했다. 유효한 GP 디스크 캐시가 있으면 정상 재사용하므로 서버를 재시작할 때 항상 GP를 다시 받는다는 뜻은 아니다.

### P2. 301 응답을 자동으로 따라간다

`communication/external/celestrak.py:10,22`는 follow_redirects=True다. 301 후 200을 반환하는 모의 시험에서는 요청 한 번이 두 번의 상류 호출이 되고 결과는 정상 수집으로 표시됐다. 현재 코드의 주소는 올바른 https://celestrak.org이며, 실제로 301을 받았다는 증거는 없다. 다만 301 발생 시 운영자에게 알리고 멈추는 동작은 없다.

### P2. 그룹 간 중복과 미등록 그룹 처리가 요청을 늘릴 수 있다

Active와 Starlink를 고르면 각각 다운로드한다. Active를 이미 받은 경우 Starlink 부분집합을 로컬에서 활용하는 경로는 없다. 또한 `data/catalog/access.py:44`는 미등록 그룹을 STATIONS로 바꾸면서 캐시 키는 요청한 그룹명 그대로 사용한다. 서로 다른 미등록 그룹 두 개로 STATIONS를 연속 두 번 다운로드하는 경로를 재현했다. 일반 UI의 고정 그룹 선택은 미등록 그룹을 보내지 않으므로 이번 현상의 직접 원인으로 단정하지 않는다.

## 화면 동작과 외부 요청의 구분

현재 궤도 화면은 초기화, 그룹 변경, 새로고침 버튼으로 GP를 조회한다 (`tabs/orbit.js:208–238,393,401,520`). 단순 카탈로그 검색과 1초 궤도 이동, 관측창 계산은 내려받은 GP를 로컬 계산하는 것이며 GP의 주기적 다운로드 루프는 찾지 못했다. WebSocket의 1.8초 재연결도 자체 서버 /ws/telemetry를 대상으로 하며 CelesTrak 요청이 아니다. 데이터 탭의 3초 모듈 조회도 CelesTrak과 별개다.

반면 임무 탭 외부 위성 검색은 350ms 입력 대기 후 /api/satellites를 호출한다 (`tabs/mission.js:417–431,447`). 성공 캐시가 유효하면 로컬 필터링만 하지만 GP 갱신이 실패하는 동안에는 여러 검색 입력이 여러 외부 시도로 이어질 수 있다. 카탈로그 화면의 그룹 변경 또는 다시 조회 안내도 오류 기간에 반복 시도를 유도할 수 있다.

## 재발 방지 제안

1. 200이 아닌 상류 응답은 즉시 공통 수집 정지 상태로 전환하고 오류 코드, URL, 최초 실패 시각을 운영자에게 알린다. GP와 SATCAT에 같이 적용한다. 301/404는 주소와 요청 조건을 확인하기 전 재개하지 않는다. 403도 무조건 반복 재시도하지 않는다.
2. 성공 시각과 정지 상태를 디스크에 보존해 서버 재시작으로 제한이 사라지지 않게 한다. 같은 PC의 여러 프로세스가 공유하는 수집 잠금 안에서 디스크 캐시를 다시 확인한다. 같은 공인 IP의 다른 PC나 프로그램까지 보호하려면 조직 단위의 공통 수집기 또는 캐시가 추가로 필요하다.
3. 화면 새로고침과 검색을 외부 강제 다운로드로 만들지 않는다. 정지 중에는 이전 GP로 계산하되 오래된 자료임을 표시하고, 캐시가 없으면 미제공으로 표시한다. 별도 서버 및 브라우저 검증에는 외부 접속이 없는 카탈로그 fixture를 기본 사용한다.
4. SATCAT 성공 결과도 지속 보관하고 실패 시 재요청을 막는다. Active와 Starlink의 중복을 줄이되 해당 그룹을 정확히 구분할 메타데이터가 없다면 임의의 이름 필터를 정확한 그룹 정보로 표시하지 않는다. 미등록 그룹은 요청 전에 거부한다.
5. 외부 요청 시각, 요청 종류, 응답 코드, 캐시 사용 여부, 다음 허용 시각을 제한된 진단 기록에 남긴다. 정상 응답 크기나 파싱 오류 역시 무한 재시도의 계기가 되지 않게 한다.

단순히 타이머를 2시간으로 바꾸거나 50회까지 기다리는 것만으로는 충분하지 않다. 공식 정책은 비정상 HTTP 응답이 발생하면 즉시 질의를 중지하고 사람이 조사하도록 요구한다.

## 재현과 검증

`python -m project_support.tools.audit_celestrak_requests`는 외부 접속 없이 위 경로를 검사한다. 결과는 `project_support/output/celestrak_request_audit.json`에 기록했다. 기존 카탈로그 시험 8개는 통과했지만 주로 성공 캐시와 단일 실패의 반환값을 검사하므로 이 반복 실패 위험을 검출하지 못했다.

전체 `python -m pytest -q`는 175개 통과(38.13초)였다.

이 문서는 검토 결과다. 당시에는 보호장치를 적용하지 않았고 서버는 종료 상태로 유지했다.

2026-09-10에 위 제안 1, 2, 3, 5와 미등록 그룹 중복 문제를 `data/catalog/request_guard.py`로 적용했다. 일정과 정지 상태를 `data/workspace/catalog_cache/request_guard.json`에 두어 프로세스 재시작과 다중 인스턴스를 함께 막고, 비정상 응답 중 다시 물어도 달라지지 않는 코드는 공급자 단위 정지로 처리한다. GP에는 If-Modified-Since를 실어 보내고 리다이렉트는 따라가지 않는다. 제안 4의 SATCAT 성공 결과 디스크 보존은 하지 않았다. 시험은 project_support/tests/test_request_guard.py 27개이며 적용 시점의 전체 결과는 184개 통과, 4개 건너뜀이다. 적용 중에도 실제 CelesTrak 요청은 보내지 않았다.
