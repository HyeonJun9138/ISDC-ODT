# 임무 탭 사용 및 계산 규칙

임무 탭은 우주 데이터 센터가 맡는 서비스 임무를 요청으로 등록하고, 군집 운용 모듈이 위성별로 배정한 작업을 일정표에 올려 실행을 지켜보는 화면이다. 위성은 노드 탭에서 `배치 완료 → 대시보드`로 반영한 내 위성이고, 지상국은 통신 탭에서 둔 지상국이며, 외부 위성은 대시보드 카탈로그(GP)에서 고른다. 지상국 접속창, 관측 통과, 식 구간, 외부 위성 교차링크 창 같은 기하는 디지털 트윈이 계산하고, 어느 위성이 언제 무엇을 할지와 실행 가능 여부의 판정은 군집 운용 모듈(ICD-03)이 맡는다. 두 역할을 섞지 않는다. 임무와 계획은 브라우저 localStorage에 저장되는 화면 구성이며 서버 런타임 상태가 아니다.

## 임무 종류

| 종류 | 요청 내용 | 배정되는 작업 | 성공 판정 |
|---|---|---|---|
| 관측 인도 | 관측 지점(프리셋 또는 위도·경도), 최대 관측각, 산출물 크기, 궤도상 처리 여부, 담당 위성 지정(선택), 인도 지상국(선택) | 촬영 → 궤도상 처리 → 보관 → (위성 간 전달) → 지상 전송 | 기한 여유, 탑재 저장 여유, 배터리 여유 |
| 궤도상 연산 | 처리 위성(선택), 입력 크기, 결과 비율 | 처리 → 보관 → (위성 간 전달) → 지상 전송 | 기한, 저장, 배터리 |
| 중계 전송 | 출발과 도착(위성 또는 지상국), 전송량, 지연 한계(선택) | 지상 상향 또는 위성 간 전달의 연쇄와 지상 전송 | 기한, 종단 지연 한계 |
| 외부 위성 데이터 수신 | 카탈로그에서 고른 외부 위성, 수신량, 교차링크 전송률, 최대 거리 | 외부 위성 수신 → 보관 → (위성 간 전달) → 지상 전송 | 기한, 저장, 배터리 |
| 군집 소프트웨어 갱신 | 이미지 크기, 적용 시간, 동시 적용 수, 대상 위성(비우면 전체) | 위성마다 지상 상향 → 갱신 적용, 동시 적용 수만큼 차수를 나눔 | 기한, 갱신하지 못한 위성 |

임무 상태는 초안(계획 없음), 계획됨(모듈 응답 있음), 실행 중(운용자가 `실행`을 누름), 완료, 기한 초과, 중단이다. 완료와 기한 초과는 저장하지 않고 분석 시각으로 판정한다. 작업 상태도 분석 시각으로 예정, 진행, 완료를 나눈다.

## 화면 사용

왼쪽 `임무 목록`은 기한이 가까운 순서이며 행의 점은 재구성 필요와 기한 초과(빨강), 실행 불가(주황), 실행 중과 완료(초록), 계획됨(파랑)을 뜻한다. 위의 칸은 전체, 계획됨, 실행 중, 완료, 주의(실행 불가 또는 재구성 필요) 수다. `＋ 새 임무`를 누르면 오른쪽에 요청 폼이 열린다. 종류를 고르고 기한(2, 6, 12, 24시간 또는 직접 입력)과 종류별 항목을 채운 뒤 `등록하고 계획 만들기`를 누르면 요청이 등록되고 곧바로 모듈에 편성을 요청한다. 외부 위성은 위성명이나 NORAD 번호로 카탈로그를 검색해 고르며, 그 위성의 GP 궤도요소가 임무에 저장되어 교차링크 창 계산에 쓰인다. 맨 아래 표시는 군집 운용 모듈의 연결 방식(내장 임시 구현 또는 외부 주소)과 응답 시간이다.

가운데 `위성 일정표`는 위성마다 한 행인 UTC 시간축이다. 옅은 하늘색 띠는 지상국 접속창, 회색 띠는 식 구간, 색 막대는 작업(촬영 초록, 처리 파랑, 보관 회색, 위성 간 보라, 지상 전송 하늘색, 상향 주황, 갱신 적용 빨강, 외부 수신 노랑)이며 빨간 세로선이 분석 시각, 주황 점선이 임무 기한이다. 선택 임무의 작업은 진하게, 다른 임무의 작업은 흐리게 그리고 실행 불가 계획의 작업은 빨간 점선 테두리를 두른다. `작업 있는 위성`과 `전체 위성`으로 행을 고르고, 6, 12, 24시간 범위를 바꾸며, `접속창 계산`은 현재 분석 시각부터 접속창과 식을 다시 계산한다. 접속창은 임무를 계획할 때도 계산되어 10분 단위로 다시 쓴다. 분석 시계는 다른 탭과 별개인 UTC 커서이며 정지, 10분 스텝, 배속, 현재 복귀를 제공한다. 배속을 올리면 작업 상태 전이를 빨리 볼 수 있다.

아래 세 칸은 선택 임무의 `검토 결과`(모듈의 검사 항목별 통과 여부와 내용, 실행 불가 사유, 제외된 위성, 재구성 필요 여부), `작업 목록`(순서, 종류, 위성, 상대, 시작, 길이, 크기, 상태), `결정 기록`(요청 등록, 계획 수신, 실행 승인, 재계획, 중단 같은 운용 기록)이다.

오른쪽 `선택 임무`는 요청 내용, 계획 창과 기한까지 남은 시간, 모듈 판정(완료 예정, 기한 여유, 작업과 위성 수, 데이터량, 경로), 진행률과 작업 사슬이다. 단추는 상태에 따라 바뀐다. `계획 생성`과 `다시 계획`은 모듈에 편성을 요청하고, `실행`은 검토를 통과한 계획을 확정해 실행 중으로 바꾸며 이후 다른 임무의 계획에서 이 작업 시간은 점유된 것으로 취급된다. 검토를 통과하지 못한 계획은 `그래도 실행`으로 확정할 수 있다. 실행 중에는 `재계획`과 `중단`이 있고, 배정된 위성이 안전 모드로 바뀌거나 배치에서 빠지면 `재구성 필요`가 붙고 `재구성` 단추가 그 위성을 제외한 채 남은 작업을 다시 배정한다. `편집`은 요청을 바꾸며 계획을 지운다.

## 역할 분담과 ICD-03

| 역할 | 위치 | 내용 |
|---|---|---|
| 임무 모델 (디지털 트윈) | `digital_twin/model_library/browser/mission_types.js` | 임무 종류와 작업 종류, 관측 지점 프리셋, 버스별 처리 속도, 대역별 상향 전송률, 정의 생성과 검증, 실행 단계 판정 |
| 창 계산 (디지털 트윈) | `digital_twin/simulation/browser/mission_windows.js` | 지상국 접속창과 전송률, 관측 통과(최대 관측각을 고각 마스크로 변환), 식 구간, 외부 위성 교차링크 창, 확정 작업의 점유 구간 |
| 배정과 판정 (군집 운용 임시 구현) | `operations_software/orchestration/` | 종류별 작업 배정, 격자 중계, 기한·저장·배터리·지연 검사, 재구성 |
| 연결 | `communication/http/orchestration.py`, `communication/external/orchestration.py`, `communication/browser/orchestration.js` | 서버 ICD 끝점, 외부 모듈 전달, 브라우저 클라이언트 |
| 표시 | `digital_twin/visualization/mission_timeline.js`, `user_application/web/scripts/tabs/mission.js`, `scripts/missions/mission_store.js` | 일정표, 화면 조립, 임무 작업 세트 |

편성 요청(디지털 트윈 → 모듈)에는 분석 시각, 임무(종류, 우선순위, 계획 창, 기한, 종류별 항목), 위성(운용 모드, 촬영 장비 여부, 처리 속도, 저장 여유, 전력, 확정된 다른 임무의 점유 구간), 지상국, 창(접속, 관측 통과, 교차링크, 식), 현재 OISL 격자(양방향 유지 중이고 런타임 장애가 없는 쌍), 장애 링크와 장애 지상국, 제외 위성이 들어간다. 요청 구성은 임무 탭과 시나리오 재생기가 공유하는 `scripts/missions/planner.js`가 맡으며, 런타임 장애가 걸린 교차링크 작업은 배정 위성이 빠졌을 때와 같이 `재구성 필요`로 표시된다. 역할 배정 결과(모듈 → 디지털 트윈)에는 작업 목록(종류, 위성, 상대, 시작과 끝, 크기, 전송률, 근거 창), 실행 가능 여부, 요약(완료 예정, 기한 여유, 경로, 위성 수), 검사 항목, 사유, 검토한 대안 수, 제외된 위성이 들어간다. 메시지 구조와 배정 규칙의 자세한 내용은 [운용 SW 임시 구현 README](../../../operations_software/README.md)에 있다. 모듈이 응답하지 않으면 계획을 만들지 않고 `미응답`을 표시한다. 브라우저에서 대신 배정하지 않는다.

### 연결 방식

기본은 내장이다. 서버가 `OrchestrationStandIn`을 프로세스 안에서 만들고 `/api/orchestration/plan`, `/commit`, `/status`로 응답한다. `실행`과 `중단`은 먼저 실행 확정·중단 통보(OR-03)를 모듈에 보내고 수락된 뒤에 화면 상태를 바꾸며, 모듈이 거절하거나 응답하지 않으면 상태를 바꾸지 않고 알린다. `python main.py --orchestration-url http://호스트:포트`로 실행하면 같은 ICD를 제공하는 외부 모듈로 요청을 전달하고, 응답이 없으면 503으로 보고한다. 설정 탭의 링크 L03(군집 오케스트레이션 ↔ 통합 프레임워크)에 원격 호스트와 포트를 지정하면 콘솔이 그 주소를 직접 호출한다.

## 계산 모델

### 창 (디지털 트윈)

지상국 접속창은 대시보드와 같은 관측창 예측(`orbit.js`의 `predictPasses`)으로 구하며, 위성의 켜진 RF 장비와 지상국 대역 중 Ka, X, S 순으로 고른 대역의 정격 전송률과 대역별 상향 전송률(S 0.5, X 20, Ka 100 Mbps)을 함께 보낸다. 관측 통과는 관측 지점을 관측자로 두고 최대 관측각 η를 고각 마스크 `acos((Re + h) / Re · sin η)`로 바꿔 같은 예측을 쓴다. 식 구간은 노드 다이나믹스의 원통 그림자 판정을 60초 간격으로 훑어 경계를 5초까지 이분한다. 외부 위성 교차링크 창은 내 위성(Kepler+J2)과 외부 위성(GP/SGP4)의 지구 고정 좌표 거리가 최대 거리 이내이고 지구에 가리지 않는 구간을 30초 간격으로 훑어 구한다. 지형, 굴절, 자세 기동 시간, 날씨는 없다. 계획 창은 기한에 1시간을 더하되 2시간 이상 24시간 이하다.

### 배정 (군집 운용 임시 구현)

배정은 결정론적 탐욕 규칙이다. 관측 인도는 촬영 장비가 켜진 위성마다 앞의 여섯 관측 통과를 후보로 삼고, 통과의 최대 고각 시각을 중심으로 45초 촬영, 이어서 `산출물 크기 × 8 / 처리 속도` 동안 처리한 뒤 결과를 내려보낼 가장 빠른 방법을 고른다. 내려보내는 방법은 그 위성의 다음 접속창이거나, 현재 OISL 격자에서 여섯 홉 안에 닿는 위성 중 더 이른 접속창을 가진 위성으로 넘기는 것이다. 위성 간 전달은 전달받는 위성의 접속창 직전에 놓아 데이터가 촬영 위성에 머물게 하며, 그 시간이 점유되어 있으면 앞으로 당겨 전달받는 위성이 보관한다. 완료 시각이 가장 이른 조합을 고르고 같으면 홉 수, 위성 번호 순이다. 궤도상 연산과 외부 위성 수신도 같은 방법으로 내려보낸다. 중계 전송은 출발과 도착의 종류에 따라 상향 접속창, 격자 경로, 지상 전송을 잇고 홉당 8 ms로 종단 지연을 어림한다. 군집 갱신은 위성마다 가장 이른 상향 접속창에 이미지를 올린 뒤 적용 시간 동안 적용하며 동시 적용 수를 넘지 않게 차수를 미룬다.

검사는 기한(완료 예정과 기한의 차), 탑재 저장(위성이 동시에 든 데이터량과 저장 여유), 배터리(작업 중 식 구간의 소비 전력과 발전을 넘는 소비를 시간으로 적분한 값이 배터리 용량의 60 % 이내), 중계 전송의 지연 한계다. 작업별 소비 전력은 촬영 150, 처리 60, 보관 30, 위성 간 전달 120, 지상 전송 90, 상향 40, 적용 40, 외부 수신 60 W다. 확정된 다른 임무의 작업 시간은 5초 간격을 두고 피한다. 안전 모드나 대기 모드인 위성과 제외로 지정한 위성은 배정하지 않고 사유를 돌려준다. 이 값들은 대표 공학값이고 실제 위성의 운용 규칙이나 자세 기동 능력을 반영하지 않는다.

## 코드 확장 규칙

- 임무 종류와 작업 종류, 프리셋, 대표 속도는 `model_library/browser/mission_types.js`에, 창 계산은 `simulation/browser/mission_windows.js`에 둔다. DOM, API, 저장소를 호출하지 않는다.
- 배정과 판정 논리는 `operations_software/orchestration`에만 둔다. 브라우저나 트윈 코드에서 작업을 배정하거나 판정을 다시 계산하지 않는다. 모듈이 없으면 계획이 없는 것이다.
- ICD-03 메시지 필드를 바꿀 때는 `communication/http/orchestration_schemas.py`, `operations_software/README.md`, `tabs/mission.js`의 요청 구성과 두 쪽의 시험을 함께 바꾼다.
- 일정표는 `visualization/mission_timeline.js`가 맡으며 주입받은 행, 창, 작업만 그린다. 화면은 일정표 영역의 실제 픽셀 폭을 재서 넘기고 폭이 바뀌면 다시 그리므로 SVG가 늘어나거나 눌리지 않는다. 행 높이는 표시할 위성이 적으면 영역을 채우도록 26~40 px 사이에서 정하고, 많으면 26 px로 두고 스크롤한다. 임무 작업 세트는 `scripts/missions/mission_store.js`, 화면 조립은 `scripts/tabs/mission.js`, 스타일은 `styles/mission.css`에 두고 `#view-mission` 범위로 제한한다.
- 기존 시나리오 임무 API(`/api/missions/*`)는 SIM 런타임의 시나리오 임무이며 REST로만 남는다. 새 임무 탭은 이 API를 쓰지 않는다.
- 실제 군집 운용 모듈이 오면 `communication/external/orchestration.py`의 주소 지정으로 연결하고 `operations_software/orchestration`은 시험 참고용으로만 남긴다.
